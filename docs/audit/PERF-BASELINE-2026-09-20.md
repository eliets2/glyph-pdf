## 2. Method

- All scenarios run OFFSCREEN (`QT_QPA_PLATFORM=offscreen`): CPU-side costs
  only, no compositor. Disclosed consequence: no frame pacing/dropped-frame
  measurement is possible in this harness (see Residuals).
- Harnesses in `tools/perf/` (committed): `perf_fixtures.cpp` (deterministic
  corpus, seed 20260920), `perf_startup.cpp` (fresh-process cold path, phase
  timers), `perf_docops.cpp` (one scenario per process so `PeakWorkingSetSize`
  is attributable to that scenario alone), `build_drivers.sh` (compiles the
  drivers with the EXACT ninja commands CMake generated for
  `tools/render_path_profile.cpp` — same Release+LTO flags, same libs;
  CMakeLists.txt untouched), `run_perf_suite.ps1` (orchestrator; samples CPU
  %, build-process count, free RAM immediately before and after EVERY block),
  `wait_quiet.ps1` (quiet-box gate).
- Startup: 20 fresh process spawns per run; the suite measures external
  wall time (process create→exit, includes loader + DLL init) AND the
  driver's internal phase timers (main()→window shown, createContext,
  MainWindow ctor).
- Document open: engine floor (`QPdfDocument::load` + page 0 rendered at 2x
  page points) and full pagination (all pages at 2x); plus the REAL app path
  `MainWindow::openDocument` timed to `pdfViewer()->pageCount() > 0` — the
  same readiness contract the GUI tests wait on.
- Core ops drive the real production engines: `PdfEditorEngine::applyRedactions`,
  the BatchMode Q1/N3 OCR skip decision (`PdfiumBackend::loadDocument` +
  `extractPageTextRuns`), `DiffEngine::compare` (150 DPI),
  `ConversionManager::convertTo` (native OOXML), `SignatureManager::signDocument`
  (local P12 `tests/fixtures/signing/test_signer.p12`, no TSA),
  `PdfEditorEngine::saveDocument`, and the full BatchMode preset pipeline
  (compress q50, 50-file corpus, isolated preset store).
- Stats: median / nearest-rank p95 / min / max over the block's samples.
  Driver limits are disclosed in each harness header (exe-qrc resources are
  null-path in the drivers; theme QSS resolves via
  `GLYPHPDF_SOURCE_RESOURCE_DIR`; QSettings isolated under org `GlyphPDFPerf`).

## 5. Findings (documented, NOT fixed — this lane optimizes nothing)

- **F1 — Startup is dominated by MainWindow construction, not engine
  bootstrap.** Of the ~106 ms median ctor, `Bootstrapper::createContext()` is
  ~0 ms; the constructor is the whole cost. Cold start (169 ms median external
  wall) is nowhere near the 2 s gate even with the driver's disclosed
  resource-loading null-paths.
- **F2 — 50-page compare is the heaviest measured operation: ~0.8–0.9 s wall,
  ~461 MiB peak WS (~9 MiB/page at 150 DPI).** The readiness review's
  concrete worry (empty overlays retained for unchanged pages, 25.245 MB for
  3 pages in its probe) remains directionally visible here as a large
  per-page footprint. This is a calibration datapoint, not a >10x-target
  regression; a per-job memory budget still needs defining.
- **F3 — Full pagination of the 100+ MB class is linear at ~9 ms/page @2x**
  (1395 ms for 150 pages). No superlinear blow-up within one process.
- **F4 — First-call jitter in signing** (median 74 ms, max 122 ms): consistent
  with one-time Windows crypto provider initialization; harmless.
- **F5 — The 16x page render succeeded at ~128 Mpx** (13472x9520, 84 ms)
  where the harness comment expected a 64 Mpx production guard to bound it —
  the guard may be scoped to the view path only. Recorded as observed;
  behaviour unchanged.
- **F6 — Environment: the D: volume hit 100% capacity mid-lane**, breaking an
  LTO link; all measurement outputs (fixtures, raw JSON, op outputs) were
  moved to `C:\perftmp` (`run_perf_suite.ps1` defaults; drivers honor
  `GLYPHPDF_PERF_OUTDIR`). Coordinator note: D: filling up is a shared-lane
  risk (repo + msys64 + all build trees live there).

## 6. Residuals (explicitly NOT covered by this baseline)

- R1: Warm-vs-cold start split (second-launch with hot OS caches), and the

  which is null-path in the driver harness.
- R2: "Office PDF" corpus with complex scans/drawings; the review asks for
  complex documents measured separately. The corpus here is synthetic text +
  noise-image payloads (real, deterministic, disclosed).
- R3: Interactive click/typing latency; R4: cancel ack/stop latency — need an
  interactive (windowed) harness, not offscreen.
- R5: Frame pacing / dropped frames; two-page view path per-scale latency.
- R6: 48 h soak + interaction latency — `feat/soak-48h` lane.
- R7: GPU-accelerated rendering paths (offscreen = software raster).
- R8: Multi-monitor/display-scale effects; battery/thermal profiles.

### 7.2 Quiet-run load honesty

Per-block load context (sampled immediately before/after each block):
open-medium through save-roundtrip — build processes 0, CPU 4–32 %. The
`open-small` block's before-sample caught the tail of a burst (2 procs, 26 %
CPU); the last three blocks (batch, mem-open, mem-compare, page-scale)
overlapped a NEW burst starting 2–4 procs at ~19:21:21 — a new build began
mid-run, as recorded. Timing impact there is negligible (batch matches its
smoke-run value; peak WS is load-insensitive and byte-comparable to the
loaded run), but the context is disclosed, not hidden. Baseline verdicts in
section 4.1 hold under the quiet numbers — every measured target has MORE
headroom in the quiet run than the provisional one.

### 7.3 What the quiet run settles

- Cold start P95 (whole process, incl. loader): **174 ms** vs the 2 s
  proposed gate — 11x headroom.
- 20-page open to first useful page P95: **8 ms** engine / **21 ms** real
  MainWindow path vs the 1 s proposed gate — ~50x headroom.
- Heaviest everyday op, 50-page compare: **807 ms median**; everything else
  users wait on interactively is ≤ 300 ms median except full pagination of
  the 100+ MB class (1298 ms, a bulk operation, not an interaction).
- Memory: 100+ MB document open ≈ **179 MiB** peak WS; 50-page compare ≈
  **461 MiB**. No numeric target existed; these are the first calibrated
  datapoints for the per-job budget definition the review asks for.
