## S1 — Signing-request sidecar (src/core/SigningRequestModel.cpp)

- Harness `fuzz/harnesses/harness_signreq.cpp`, corpus `fuzz/corpus/signreq/`
  (36 seeds: valid, magic/value/type mutations at every field, dup keys,
  5000 signers, 1 MB strings, 2000-deep nesting, BOM, unicode/path-shaped names).
- 1120 execs: 1067 REJECT (fail-closed handshake held), 36 clean OK, 17 finding
  execs → one bucket.
- **FINDING (ACCEPTS-INVALID) — magic VALUE is never verified.**
  `fromJson` tests only `magic.isUndefined()` (SigningRequestModel.cpp:134-138);
  the class contract (SigningRequestModel.h:29-32) requires the pair
  `"glyphpdf-signrequest": 1`. `"glyphpdf-signrequest": 999 / 1.5 / true /
  null / "one"` all decode as valid requests. Duplicate-key mutants show Qt
  keeps the LAST occurrence, so `"glyphpdf-signrequest": 1, …,
  "glyphpdf-signrequest": 2` is accepted with magic 2.
  Practical severity LOW today (schemaVersion is still checked strictly), but
  the handshake does not implement its own documented contract.
- Evidence + 2 preserved seeds + repro:
  `fuzz/findings/w1/s1-signreq-magic-value-accepted/`
- Everything else clean: no crash/hang/OOM; round-trip `toJson→fromJson`
  self-consistency held for every accepted model; shape invariants held.

## S2 — BatchPreset codec + name rendering (src/core/BatchPreset.cpp)

- Harness `fuzz/harnesses/harness_batchpreset.cpp`; corpus `fuzz/corpus/batchpreset/`
  (69 seeds: V1–V9 diagnostic paths, range edges at every boundary, unknown keys
  at every level, type confusions, naming templates, regex abuse, 256 KiB cap).
- Campaign 2176 execs (9 finding execs) + a deterministic `probes` mode: fixed
  matrix of 4 hostile templates × 20 hostile basenames = **67 violations**.
- **FINDING (ACCEPTS-INVALID, path containment) — template literals escape the
  output dir.** `sanitizeNameComponent` guards token VALUES only
  (BatchPreset.cpp:64-75); the template's literal characters are copied
  verbatim (BatchPreset.cpp:117-118). `parse()` accepts presets whose
  `output.naming` is `..\..\{basename}.pdf` / `../../{basename}.pdf` /
  `C:\{basename}.pdf` / `{basename}/{n}.pdf`, and `resolveNaming` renders them
  verbatim — violating BatchPreset.h:94 ("a FILE NAME — no directory
  components"). Consumer BatchMode.cpp:961 joins the rendered name with
  `QDir(outDir).filePath(name)` → the batch output lands outside the chosen
  output dir (path shown in the overwrite dialog, so user-visible — a
  defense-in-depth break, not a silent one).
- **FINDING (data loss) — reserved DOS device names survive token
  sanitization:** `{basename}` = CON/NUL/AUX/COM1/LPT1 renders `CON.pdf`,
  `NUL.pdf.pdf`, … — writing such an output goes to the device, reported as
  success.
- **FINDING (minor) — unbounded rendered length:** 60 000-char and {date}×4000
  templates parse clean and render >240-char names (late Win32 failure).
- Evidence + 4 preserved seeds + probe-matrix output:
  `fuzz/findings/w1/s2-batchpreset-naming-escapes/`
- Clean: the V1–V9 fail-closed diagnostics refused every unknown key / wrong
  type / out-of-range value / unimplemented enum in all 2176 execs; codec
  round-trip and `idFromName` slug grammar held everywhere.

## S3 — Accessibility scan/fix (src/engines/AccessibilityChecker.cpp, AccessibilityFixes.cpp)

- Harness `fuzz/harnesses/harness_a11y.cpp`; corpus `fuzz/corpus/a11y/`
  (8 fixtures: untagged baseline, tagged+/MarkInfo false+image w/o /Alt, form
  XObject cycle, /Lang-/ViewerPreferences-/Info type confusions, /TU gaps,
  /Fields wrong type, broken xref) + `fuzz/corpus/a11y-crashers/` (4 crafted
  field-walk killers). Each exec also drives `applyAccessibilityFix` 11× with
  hostile parameters (page -1/9999, traversal resource names, 20 KB language,
  100 KB /Alt text) on a fresh copy.
- 256 campaign execs + crasher runs. Two crash-class buckets:

- **FINDING (CRASH/DoS) — cyclic /Fields hierarchy kills the process.**
  `collectFieldGaps` (AccessibilityChecker.cpp:137-178) recurses on /Kids with
  NO depth cap and NO cycle detection (the image walk got both; the field walk
  got neither) and accumulates `parentName + "." + ownName` at every level.
  A mutual or self /Kids cycle → unbounded recursion → uncaught
  `std::bad_alloc` (heap) or hard SEGV (stack) — which one loses the race
  varies per run. In-app: opening the accessibility panel of a crafted PDF
  terminates GlyphPDF. Crashers kept in `fuzz/corpus/a11y-crashers/`.
  Evidence + segfault seed: `fuzz/findings/w1/s3-a11y-field-cycle/`

- **FINDING (CRASH-class) — scanAccessibility leaks PdfError past its
  "never throws" contract.** Only the initial `doc.Load()` is wrapped; later
  lazy parses (`GetCatalog()` / `GetTrailer()` / traversal) throw
  `PdfError::InvalidObject / BrokenFile / InvalidDataType / InvalidNumber`
  out of the function, violating AccessibilityChecker.h:71 and terminating
  callers that rely on the contract. 6 reproducing mutants preserved from 4
  distinct base fixtures; 6/6 reproduce from a single seed each.
  Evidence: `fuzz/findings/w1/s3-a11y-scan-throws/`

- **Held clean (the checks the mission called out):** the Form-XObject
  depth-8 cap held — a crafted Form XObject cycle (A↔B) plus mutants all
  returned without crash (32/32); the bounded-sample caps (50 images / 50
  fields) were never exceeded; every finding carried checkId+whyNot;
  `applyAccessibilityFix` never threw, never produced an unreadable "fixed"
  doc, and honestly refused every hostile request.

## Surfaces NOT fuzzed (and why)

- **SigningRequestRunner / SecurityController enforcement seams** — out of the
  five-surface scope; they consume S1's model (the decode layer is covered).
- **quickjs-ng form-JS surface** — has its own W1-adversary lane
  (pdf-r18); not duplicated here.
- **PDFium/PoDoFo/qpdf container-level differential oracle** — the G19 rig
  lists it as scaffolded-but-unwired; container fuzzing of the vendored
  engines (third-party target) is out of this agent's charter beyond the
  GlyphPDF-owned code paths exercised above.
- **Sanitizer builds** — ASan/UBSan/libFuzzer remain unavailable on ucrt64
  (no compiler-rt; unchanged since the G19 manifest). Findings above are
  deterministic logic/crash findings reproducible without sanitizers; the
  hand-link recipes in `fuzz/build_clang/` remain the documented path when a
  clang toolchain is installed.
