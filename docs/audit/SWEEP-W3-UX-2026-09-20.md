## Code-level pre-findings (from the source survey; verified by runs below)

These are observations from reading the flow surfaces before/at harness time;
each is confirmed, refuted, or annotated by the run evidence above.

- **Accessibility disclosure box** (`AccessibilityPanel.cpp:97`): "Detection
  only. … never certifies PDF/UA. Content tagging … is not yet available."
  The honesty box bounds the claim correctly IF the rest of the panel never
  overclaims (run F7 checks the fix loop and the zero-gaps wording "This is
  not a PDF/UA verdict").
- **Find & Replace contract** (`FindReplaceDialog.cpp:248`): count is shown
  BEFORE replace ("count shown before replace"), replace-all reports applied
  count + geometry/length-reflow warnings (moat M8). Count/Replace buttons are
  disabled when scope is unusable (packa-F1).
- **Redaction partial failure** (`RedactApplyDialog.cpp:410-460`): a failed
  sanitization gets a LABELED partial-result dialog (Retry Sanitize / Keep
  Redacted File / Discard Output), never a generic success banner; a FAILED
  proof gets its own critical ("Do NOT distribute this file…"). D01: after a
  successful retry the flow is never re-announced with the stale failure
  wording.
- **Save** (`HomeController.cpp:145-346`): external-change conflict gets a
  resolution dialog (Save As / Reload / Cancel) — "A silent overwrite is
  impossible"; save FAILURE is a modal, not a transient status (UX-14).
- **Cert-encrypt** (`CertEncryptController.cpp:50-160`): OK is gated on >= 1
  VALID recipient; ER-3 multi-recipient re-encryption warning discloses the
  session-key consequence BEFORE the dialog; engine failure = honest critical
  with "The original file was left unchanged."
- **Batch** (`BatchMode.h/.cpp`): skip-already-text is its own accounting
  bucket ("never counted as success OR failure"); W1-01: a preset's
  `onConflict: overwrite` NEVER bypasses the interactive overwrite confirm
  ("There is no silent overwrite"); capability-unavailable steps are DISPLAYED
  at selection and REFUSED at run with the registry's whyNot.
- **Signing** (`SigningRequestRunner.h`): mutation gate re-confirms SHA-256 at
  every step; coverage honesty — after signing, the step validates the signed
  bytes and records ONLY engine-attested facts; the progress panel is
  modeless "guidance, never a gate", with the advisory-order disclosure.
- **OCR single-page** (`OCRMode.cpp:765,820`): a zero-word recognition
  completes the run as an explicit retryable Idle ("OCR complete — no text
  recognized on this page") instead of stale stats. The skip-already-text
  DISCLOSURE exists in BATCH (own bucket) — the single-page screen has no
  already-text disclosure (F5 probes what a user actually sees).

## Friction inventory (ranked)

1. **[F4d-D1] BROKEN FLOW — the 2-signer prepare-signing-request workflow cannot
   complete: the fill step's in-place commit is denied while the document is open.**
   The first fill step fails with `The signature field sig1 could not be placed:
   commit to destination failed: Access is denied.` (both driven steps fail
   identically; the panel stays "pending"; engine signatures on the document: 0).
   Root cause (traced by the resume lane): `SigningRequestRunner::runFillStep` does
   its LAZY FIELD PLACEMENT + commit **from the signing worker thread**
   (`SignatureFieldCreator::createSignatureFields(in.docPath, …, in.docPath)` →
   `SafeSave::commitFileToDestination`), and the SafeSave GUI handle coordinator
   **deliberately no-ops off the GUI thread** (`QThread::currentThread() != thread()`
   guard, `GpMainWindow.cpp:~226`). The viewer's open `QPdfDocument` therefore keeps
   the destination locked and the atomic replacement is denied. The workflow is only
   reachable WITH the document open (the progress panel lives in-app), so a
   first-time user cannot complete a signing request — ever. The failure disclosure
   itself is HONEST (names the field + the engine reason; "the document is
   unchanged" holds). **Fix direction (recorded for fix lanes; NOT a message-text
   fix):** extend handle coordination to background commits (park/restore the viewer
   document around the fill-step dispatch, or hop the commit to the GUI thread) —
   the same boundary save-in-place and redaction commits already use.
   Harness: gated as `QEXPECT_FAIL` (XFAIL) in `flow4_…` — it becomes XPASS when a
   fix lane resolves it; remove the marker + this finding together.
2. **[F2b-D1] FIRST-RUN PRESET SAVE FAILS — opaque error, no recovery. FIXED
   2026-09-21.** `BatchPresetStore::save`/`rename` (`src/core/BatchPreset.cpp`)
   never created their root dir. On a clean profile the first-ever "Save as
   Preset" failed with `…: cannot open for writing — The system cannot find the
   path specified.` **Fix landed by the resume lane:** `QDir().mkpath(m_rootDir)`
   at the save AND rename boundary (the store owns its root). Pinned by
   `TestBatchPresets::firstSaveOnCleanProfileCreatesStoreRoot` (store constructed
   against a NOT-YET-EXISTING nested root): fail-before observed (pin FAILED
   pre-fix with the exact opaque error), 15/15 green post-fix, negative control
   re-verified (revert → pin FAIL → restore → 15/15). Evidence:
   `evidence-w3-ux/ux-pin-f2bd1.txt`.
3. **[F6-F1] Opening the app's OWN certificate-encrypted output dead-ends with a
   misleading generic error.** The landed artifact is genuinely encrypted
   (verified: trailer `/Encrypt`, `/Filter /PubSec`, recipient envelopes present),
   but reopening it fails with `ERROR — Could not open the PDF document. File: …`
   — the same wording a corrupt file gets. The viewer cannot decrypt PubSec
   documents, and the error never says so; a user who JUST encrypted a file is
   told it "could not be opened" with zero mention of certificates. **Fix
   direction:** at the load-failure path, detect a PubSec `/Encrypt` dictionary
   and name the real state ("encrypted to recipient certificate(s) — open in a
   viewer with a matching certificate"); not a trivial message-text fix (needs
   the detection branch), recorded for fix lanes.
4. **[F5-F2 + F5-F1] OCR: default preprocessing zeroes recognition on a clean scan;
   cold engine init is a multi-minute silent wait.**
   (a) With the shipped defaults (deskew + binarize + denoise ON) the ensemble
   completed in seconds with `OCR Complete. 0 text blocks detected.` on a clean,
   scanner-scale page ("OCRME 42", ~21pt, 1:1 raster); with the SAME page and the
   screen's own preprocessing checkboxes OFF, recognition succeeds immediately
   (3 blocks, "OCRME 42 OCRME 42"). Evidence: `ux-f5.txt` vs the interim runs — a
   first-time user with a clean scan gets ZERO text by default. Recorded for fix
   lanes (preprocessing-quality, not message text). (b) Cold engine init
   (up to 3 ONNX sessions + Tesseract) took minutes on first-ever use across this
   audit's runs, with only a status-bar transient for feedback; on warm caches the
   same run takes ~3–5s. Related: the OCR review screen's lifecycle message
   (`m_lastLifecycleMessage`, `OCRMode.cpp:542`) is set but NEVER displayed
   anywhere (dead disclosure path — failures surface only as a 7s status-bar
   transient).
5. **[F2a-F1] The merge completion modal asks "Would you like to open the output file?"
   but never NAMES the output** — the filename is only in a 5-second status-bar transient
   (`Successfully merged %1 files to %2`). A first-time user who misses the transient
   does not know where the merged file went. Fix: include the output path in the modal
   text (the modal already exists; add `.arg(outputFile)`).
6. **[F1-F1] Offscreen drag limitation (harness note, not a product finding):** the
   highlight drag did not place a mark under the offscreen platform; the suite staged
   the annotation through the production annotation model and the SAVE half of the flow
   is fully verified. Native confirmation still outstanding (same residual the R16 lane
   recorded).
